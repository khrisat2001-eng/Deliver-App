# 07 — منطق توزيع الرحلات (Trip Matching Logic)

التنفيذ والاختبارات: `packages/core/src/matching.ts`.

## 1. الخطوات

```
1. العميل يؤكد الطلب → Trip(status=SEARCHING), round=0
2. جلب المرشحين من Redis GEO:
     GEOSEARCH drivers:online:{city}:{vehicleType} FROMLONLAT … BYRADIUS radius[round]
3. الفلترة (eligibility)
4. حساب ETA الحقيقي لأفضل 10 مرشحين عبر Distance Matrix من مزوّد الخرائط
5. حساب النقاط (score) والترتيب
6. إرسال العرض لأفضل سائق (أو batch) عبر WebSocket + Push عالي الأولوية
7. جدولة مهمة "انتهاء المهلة" في BullMQ بعد offerTimeoutS
8. النتيجة:
     قبول → قفل الرحلة (أول من يقبل يفوز) → DRIVER_ASSIGNED
     رفض/انتهاء → إضافة السائق لقائمة المستبعدين → العودة للخطوة 3 بنفس الجولة
     لا أحد في هذا النطاق → الجولة التالية بنطاق أوسع
     انتهت الجولات → NO_DRIVER_FOUND + إشعار العميل
```

## 2. شروط الأهلية

| الشرط | السبب عند الرفض |
|---|---|
| حساب السائق `APPROVED` | `not_approved` |
| الحالة `ONLINE` (ليس BUSY أو ON_TRIP) | `not_online` |
| نفس المدينة | `wrong_city` |
| يملك سيارة مفعّلة من النوع المطلوب | `wrong_vehicle_type` |
| مستنداته سارية | `documents_invalid` |
| لم يُعرض عليه هذا الطلب سابقًا | `excluded` |
| العميل لم يحظره (تقييم 1 نجمة = عدم المطابقة مجددًا) | `blocked` |
| رحلة نقدية ودين العمولة فوق الحد | `cash_debt` |
| داخل نطاق البحث | `too_far` |
| ETA للوصول ≤ 15 دقيقة | `eta_too_long` |

## 3. حساب النقاط

```
score = 0.60 × (1 − ETA / maxETA)
      + 0.15 × (rating − 1) / 4
      + 0.15 × acceptanceRate
      + 0.10 × min(idleTime / 30min, 1)
```
- **ETA هو العامل الأهم** (الطريق الفعلي وليس الخط المستقيم، بسبب الأنهار والجسور ونقاط التفتيش).
- **وقت الانتظار (idle)** يوزع الرحلات بعدل: السائق الذي لم يحصل على رحلة منذ مدة يتقدم قليلًا.
- كل الأوزان والنطاقات والمهلات قابلة للتعديل من لوحة التحكم لكل مدينة.

## 4. الإعدادات الافتراضية

| الإعداد | الافتراضي |
|---|---|
| نطاقات الجولات | 2 كم ← 4 كم ← 7 كم |
| عدد السائقين لكل عرض | 1 (إرسال متسلسل) — يمكن رفعه إلى 2–3 في أوقات الذروة |
| مهلة القبول | 15 ثانية |
| الحد الأقصى للبحث الكلي | 3 دقائق |
| أقصى ETA | 15 دقيقة |
| حد دين العمولة النقدية | 50,000 د.ع |

## 5. التزامن وسلامة البيانات

- **قفل الرحلة**: القبول يتم بـ `UPDATE trips SET driverId=?, status='DRIVER_ASSIGNED' WHERE id=? AND status='SEARCHING'`؛ إذا تأثر 0 صف فالرحلة أُخذت.
- **قفل السائق**: `SET driver:lock:{id} tripId NX EX 30` يمنع وصول عرضين لنفس السائق في نفس اللحظة.
- عند قبول السائق تُزال من Redis GEO المتاحين فورًا، وتعود عند انتهاء الرحلة.
- السائق الذي يرفض أو يتجاهل العروض تنخفض نسبة قبوله (تؤثر على الترتيب، وعند حد معين يُحوَّل Offline تلقائيًا بعد 3 تجاهلات متتالية).
- إلغاء السائق بعد القبول ← الرحلة تعود `SEARCHING` تلقائيًا مع استبعاده، والعميل لا يحتاج لإعادة الطلب.

## 6. تحسينات لاحقة (بعد الإطلاق)

- **Batch matching**: كل 2–3 ثوانٍ تجميع الطلبات والسائقين في منطقة وحل مسألة إسناد (Hungarian) لتقليل مجموع الـ ETA.
- **رحلات متتالية**: عرض رحلة جديدة على سائق يوشك على إنهاء رحلته قرب نقطة الانطلاق.
- **توجيه السائقين** إلى مناطق الطلب العالي (Heatmap + حوافز).
